# 운용 로버를 유지하며 개발하기 {#운용-로버를-유지하며-개발하기}

[프로젝트 개요]({{< ref "docs/global-update-project/ko/_index.md" >}}) · [English]({{< ref "docs/global-update-project/en/workflow.md" >}})

**일상적인 개발 중에는 NX 로버의 현재 운용 환경을 유지합니다.** 새 OS 설치, 재플래시, 서비스 설정 변경, 실제 Jetson에서의 연동 시험은 Nano에서 진행합니다. 코드 수정과 시뮬레이션은 개발자 PC에서 병렬로 진행합니다.

{{< mermaid >}}
flowchart LR
    W[개발자 PC] --> C[검토한 코드와 시험 환경]
    N[Nano 시험 장비] --> C
    C --> Q[합의한 시간에 NX 시험]
    Q --> F[로버 통합 시험과 필드 검증]
    F --> R[팀 승인 후 운용 환경 전환]
{{< /mermaid >}}

## Humble과 Jazzy 코드를 함께 관리하기 {#두-개발-계열을-유지합니다}

현재 운용에 필요한 Humble 코드는 계속 유지보수하고, Jazzy는 별도 저장소와 개발 환경에서 작업합니다. [마이그레이션 fork](https://github.com/URC-kaist/mr2-stack-jazzy)의 기본 브랜치는 `main`입니다. 이력을 이어받았으므로 기존 코드를 참고하고 수정 사항을 추적할 수 있습니다. 최종적으로 어느 저장소를 기준으로 삼을지는 팀이 정합니다.

이 자료를 준비한 로컬 `~/mr2-stack-jazzy`에서는 `origin`으로 fork를 추적합니다. `upstream`은 `URC-kaist/mr2-stack`에서 fetch하도록 설정했으며, 이 로컬 설정의 push URL은 비활성화했습니다.

시작점은 조사한 commit `74422f36c55140519f111cf6709f1725711b536a`입니다. 로컬에는 `audit/2026-11-14` 태그도 붙였습니다. 아직 최종 통합 기준은 아닙니다. 분야별 코드를 합치기 전에 rover-direct 작업과 실제 NX 운용 환경의 차이를 어떻게 반영할지 정해야 합니다.

작업은 작은 브랜치와 PR로 나누고 리뷰를 거쳐 반영합니다. 현재 운용에도 필요한 수정은 적절한 경우 Humble 쪽에 먼저 넣은 뒤, 합의한 merge/cherry-pick 절차로 Jazzy에 반영합니다. Jazzy에만 필요한 변경은 마이그레이션 저장소에서 관리합니다. 저장소를 나누었다고 전면 재작성까지 해야 하는 것은 아닙니다.

## 개발 환경과 공통 인터페이스 분리하기 {#환경을-분리하고-공통-규약을-맞춥니다}

22.04/Humble과 24.04/Jazzy는 기존 설치 결과가 섞이지 않는 환경에서 각각 구성하세요. 셸과 `build`, `install`, `log` 디렉터리를 따로 사용합니다. 한 셸에서 두 ROS 설치를 함께 source하거나, 한 환경에서 빌드한 바이너리 overlay를 다른 환경에 재사용하면 안 됩니다.

컨테이너는 사용자 공간의 설치와 실행 조건을 재현하는 데 도움이 됩니다. BSP와 실제 장치의 동작은 해당 장비에서 확인해야 합니다.

개발용 ROS 그래프와 명령·네트워크 연결은 운용 로버와 격리합니다. 메시지, TF(좌표계 간 변환), launch, 프로토콜, 운용 모드·센서·서비스 조합을 바꿀 때는 통합 담당자와 합의하세요. mock을 사용하는 시험 외에 실제 ROS를 연결한 시험도 필요합니다.

## 다른 팀원이 같은 절차로 재현해 보기 {#첫-재현성-실습}

빌드 담당자가 설치·설정 절차와 대표 시나리오 하나를 준비합니다. 다른 팀원은 기존 설치 결과가 없는 환경에서 이 절차를 따라 해 봅니다. 소스·서브모듈 버전, 의존성을 받은 곳, 런타임 버전, 실행한 명령과 결과, 아직 남은 장치 시험을 기록합니다.

아래 명령은 **Noble/Jazzy 설치와 환경 구성을 마친 뒤 사용할 점검 순서**입니다. 전체 설치 절차는 아니며, 현재 코드가 통과한다고 확인한 명령도 아닙니다.

```bash
# 필요하면 다시 구성할 수 있는 Noble/Jazzy 개발 환경에서 실행합니다. 로버 NX에서는 실행하지 않습니다.
source /opt/ros/jazzy/setup.bash
cd ~/mr2-stack-jazzy/rover/ros2_ws
rosdep install --from-paths src --ignore-src --rosdistro jazzy -y
colcon build --symlink-install --event-handlers console_direct+
source install/setup.bash
colcon test --event-handlers console_direct+
colcon test-result --verbose
```

의존성 설치가 실패하면 원인을 확인하세요. 많은 항목을 skip 목록에 넣어 실패를 가리지 않습니다. 먼저 주요 경로의 기본 동작을 확인하는 smoke test 하나를 정하고, 이를 막는 기존 결함부터 해결합니다. 구현이 진행되면 점검 범위를 넓힙니다.

## 공유 Nano 사용 전후에 할 일 {#공유-nano-사용-규칙}

예약할 때 소스 버전, OS 이미지, 주변장치, 예상 시간, 재부팅·재플래시 여부를 남기세요. 사용하는 동안 OS/BSP와 시스템 전체의 의존성을 누가 변경할지도 정합니다.

작업 후에는 기준 환경으로 복구하거나, 다음 사용자가 현재 상태를 알 수 있도록 인계 기록을 남깁니다. 운용 로버에 필요한 장비를 빼 오기보다 전용 시험 장치, 기록 데이터 재생, mock을 활용합니다.

## NX 시험은 준비와 복구 시간을 확보한 뒤 진행하기 {#준비된-nx-검증-시간}

NX에만 해당하는 지원 조건과 설정은 운용을 방해하지 않는 범위에서 미리 조사합니다. 실제 NX 시험 전에 다음을 준비하세요.

- 검토한 코드·설치 이미지·설정 묶음과 관련 Nano 시험 결과
- 이번에 확인할 항목, 장비 구성, 시험을 중단할 조건
- 부트 펌웨어 호환성을 고려한 복구 절차와 복구에 필요한 시간

팀과 일정을 합의한 뒤 시험합니다. 운용 환경 전환을 별도로 승인받은 경우가 아니라면 시험 후 기존 환경을 복구하세요. Nano에서 복구에 성공했더라도 NX 복구 절차는 NX에서 따로 확인해야 합니다.

시험 시간을 확보하지 못하면 NX 전용 항목은 미완료로 남기고 독립적인 개발을 계속합니다. NX가 한 대뿐이므로 최종 운용 환경을 교체하는 동안까지 무중단을 보장할 수는 없습니다.
