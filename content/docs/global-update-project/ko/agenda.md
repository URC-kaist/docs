# 첫 회의에서 정할 일 {#착수-회의-안건과-공유-문안}

[프로젝트 개요]({{< ref "docs/global-update-project/ko/_index.md" >}}) · [English]({{< ref "docs/global-update-project/en/agenda.md" >}})

이 자료는 팀이 프로젝트 내용을 검토하고 함께 작업을 시작하기 위한 안내입니다. 마이그레이션이 완료되어 승인을 요청하는 단계는 아닙니다. 기술 내용은 영어 원문을 기준으로 정리하고 한국어로도 제공합니다.

## 회의에 필요한 사람과 준비 {#요청할-협의}

현 SW 팀장 `@yongwhan-chung`이 개발자 배정, 투입 가능한 시간, Nano를 가져오는 일을 조율합니다. HW 담당자와 로버 운용자도 참여해 실제 장치 시험에 필요한 준비와 로버를 사용할 수 있는 시간을 함께 정합니다.

문서에 이름을 적었다고 작업 배정이나 알림 발송까지 이루어진 것은 아닙니다. 실제 배정과 참여 일정은 팀에서 확인해야 합니다.

## 회의에서 답할 질문 {#회의에서-남길-결과}

| 주제 | 정하고 기록할 내용 |
| --- | --- |
| 목표와 범위 | 첫 릴리스에서 어떤 기능과 운용 구성을 지원할까요? 새 기능 실험은 어디까지 포함할까요? |
| 기준 코드와 현재 로버 | NX에 설치된 코드·설정은 어떻게 기록할까요? 기준 commit과 rover-direct 변경은 어떻게 정리할까요? |
| 시험 장비 | Nano를 언제 가져와 누가 사용할까요? 장비 구성, 전용 주변장치, NX 운용 유지 원칙은 무엇인가요? |
| 저장소 | fork를 누가 관리하고, 기존 코드의 수정을 어떻게 가져올까요? 이슈는 어디에 모을까요? |
| Project와 파일 | Project의 관리자·접근 권한, 첫 작업 배정, 결과 파일 보관 위치는 어떻게 정할까요? |
| URC 2027 준비 | 언제까지 어떤 상태를 만들까요? HW 담당자·운용자가 참여할 통합 시험은 언제쯤 진행할까요? |

실제 날짜, 참여 가능한 인원, 약속할 작업량은 팀이 정합니다. 전면 재작성을 제안한다면 별도의 기술 근거를 검토합니다. 마이그레이션을 시작하기 위해 전면 재작성을 먼저 결정할 필요는 없습니다.

## 첫 결과로 확인할 것 {#처음-입증할-중간-결과}

첫 목표는 다음 세 가지입니다.

1. 현재 NX의 코드·설정을 기록하고, 옮길 기능과 기준 소스를 정합니다.
2. Nano를 개발·시험에 사용할 수 있도록 준비합니다.
3. 다른 팀원도 따라 할 수 있는 설치·빌드 절차와 실제 Jetson에서의 smoke test 하나를 만듭니다.

결과와 로그를 검토하고 작업량 추정을 고친 뒤 분야별 병렬 작업을 넓힙니다. 진행 상황을 공유할 때는 무엇을 재현하거나 검증했는지, 다음에 어떤 결정이나 시험이 필요한지를 알려 주세요.

## 팀에 공유할 안내 문안 {#공유-문안-제안}

> URC 2027 준비를 위한 MR2 글로벌 업데이트 안내를 정리했습니다. 목표는 Ubuntu 24.04 / ROS 2 Jazzy / Gazebo Harmonic입니다. 새 환경은 Nano에서 개발하고 시험하며, 기존 NX 로버는 계속 운용할 수 있도록 유지합니다.
>
> 프로젝트 개요와 분야별 작업을 읽어 주세요. 첫 회의에서는 기준 코드와 범위, Nano 사용 준비, 저장소·Project 관리, 초기 작업 배정, SW·HW 공동 시험 계획을 정하려고 합니다.
>
> [Project](https://github.com/orgs/URC-kaist/projects/2)와 [마이그레이션 저장소](https://github.com/URC-kaist/mr2-stack-jazzy)는 준비되어 있습니다. 착수 이슈의 담당자는 팀에서 배정해야 합니다. 아직 로버를 업데이트한 것은 아닙니다.

공유할 때는 실제 게시된 문서·Project·저장소 링크를 사용하세요. 초안에 남은 로컬 경로나 아직 만들지 않은 주소가 없는지 확인합니다.
