# SW/HW 공동 검증과 릴리스

[프로젝트 개요]({{< ref "docs/global-update-project/ko/_index.md" >}}) · [English]({{< ref "docs/global-update-project/en/acceptance.md" >}})

인수는 공동 시스템 활동입니다. SW는 후보 환경과 소프트웨어 근거를 준비하고, HW 통합은 물리 구성·준비 상태를 확인하며, 로버 운용 담당자는 접근과 물리 시험을 조정합니다. 결과 인수와 릴리스 권한자는 팀이 정합니다. 인력 배정은 해당 팀 리더의 역할입니다.

## 필요한 기능을 먼저 정합니다

첫 릴리스의 운용 프로파일을 합의하고 기능별로 필수, 연기, 실험을 구분합니다. 운용 기준, 시나리오, 기대 결과·허용오차, 장비, 참여자, 근거를 기록합니다. UI placeholder나 설정된 모든 스트림을 자동으로 필수 요구사항으로 취급하지 않습니다.

| 관문 | 대표 근거 |
| --- | --- |
| 재현성 | 클린 빌드·설정 기록, 소스·의존성 버전, 독립 재현 |
| 제어와 Servo | 매개변수·인터페이스, 수명 주기, 명령 모드, 단위·방향·제한, 오래된 명령과 제어권 전환 |
| 시뮬레이션과 자율 주행 | spawn/clock/sensor, TF, 위치 추정·주행 가능성 처리, 필요한 임무 경로와 실패·취소 동작 |
| 통신/UI | 네이티브 ROS relay, 명령·텔레메트리, 연결 해제·재연결, 의도한 배포 프로파일 |
| 카메라/추론/영상 | 필수 센서, 대상 환경에서 생성한 모델 산출물, NX 인코더, 합의한 동시 부하 |
| 네이티브 서비스 | 장치 준비, cold boot, 재시작·재연결, 지속 운용 |
| 공동 로버/필드 | 필수 종단 간 모드, 물리 동작, 운용 절차와 복구 |

명령 유효 시간, 제어 주기, 지연, 정확도, 자원·열 한계는 임무 요구와 기준 동작의 측정 결과로 정합니다. 유사한 부하 조건의 근거를 남기며 보편적인 통과 수치를 임의로 채택하지 않습니다.

## 환경별로 입증할 수 있는 범위

워크스테이션은 해당 환경의 소프트웨어·시뮬레이션 통합을 입증합니다. Nano는 arm64/NVIDIA 스택과 연결 장치의 네이티브 근거를 더합니다. NX 하드웨어 인코딩, 물리 인터페이스, 실제 운용 부하, 필드 관문은 실제 NX/캐리어/로버에서만 완료할 수 있습니다.

통과 결과를 분리해 기록하고, 해당 없음은 이유를 남깁니다. 소프트웨어나 Nano 결과를 NX 인수로 조용히 바꾸지 않습니다. 소스·서브모듈 SHA, 이미지/BSP/커널, 런타임·의존성 버전, 전력 모드, 입력·설정, 명령, 관측 결과, 운용자, 시각을 기록합니다.

## 정비 시간과 복구

개발 중 NX 가동을 보호합니다. 중단이 필요한 시험 전에는 후보 묶음, 해당 Nano 결과, 정확한 목표, 물리 설정, 중단 조건, 복원 절차, 참여자와 시간을 검토합니다. 복구 계획에 부트 펌웨어 호환성을 포함하며, SSD 복사만으로 충분하다고 가정하지 않습니다.

복원, 진단, 재시험 시간을 확보합니다. 전환을 별도로 합의하지 않았다면 시험 후 기존 운용 환경을 복구하고 필수 기능을 확인합니다. Nano의 복구 연습 성공은 NX 복구의 증명이 아닙니다. 시간을 확보하지 못하면 해당 대상 검증을 대기 상태로 둡니다.

## 서로 다른 세 가지 이정표

1. **착수 자료 공유:** 프로젝트 설명, 선호 방향, 리더 결정 사항, 초기 작업을 팀에 보이게 합니다.
2. **구현 중간 결과 인수:** 검토된 소스와 명시한 환경·기능의 근거를 확보합니다.
3. **로버 전환:** 필요한 공동 NX/필드 관문, 검증된 배포·복구 묶음, 운용 준비, 정비 시간, 팀의 릴리스 결정을 갖춥니다.

자료 공개가 3번 완료를 뜻하지 않습니다. 시험, 수정, 재시험은 별도 투입 여력이 필요한 명시적인 프로젝트 업무입니다.
