# 분야별 작업과 협업 {#결과와-근거를-단위로-업무를-나눕니다}

[프로젝트 개요]({{< ref "docs/global-update-project/ko/_index.md" >}}) · [English]({{< ref "docs/global-update-project/en/work-packages.md" >}})

**담당자와 투입 가능한 시간은 SW 팀장 `@yongwhan-chung`이 정합니다.** 아래는 작업을 나누기 위한 제안입니다. 분야마다 한 명씩 필요하다는 뜻은 아니며, 한 사람이 여러 역할을 맡을 수 있습니다.

프로젝트 요청자는 Yongwhan에게 재설정 가능한 여분의 Nano를 가져와 달라고 요청했습니다. 장비를 가져와 시험 준비를 마쳤는지는 아직 확인되지 않았습니다.

### 플랫폼과 빌드

Humble/Jazzy를 처음부터 구성하는 절차, 의존성 버전 고정, CI, Nano 설치를 맡습니다. Linux·Jetson·빌드 환경을 다룰 수 있어야 합니다. 현재 코드와 NX 환경을 기록하고 Nano를 준비하는 일부터 시작합니다. 다른 분야가 같은 환경에서 개발하고, 새 팀원도 빌드와 배포를 재현할 수 있게 만드는 역할입니다.

### Navigation과 Simulation

Jazzy의 Nav2·BT 설정, 위치 추정, traversability(지형 주행 가능성) 처리와 Gazebo Harmonic을 맡습니다. 개발자 PC에서 시나리오를 준비하는 작업은 Jetson 연동과 병렬로 진행할 수 있습니다. 제어·센서 인터페이스는 관련 분야와 맞춥니다. 반복 가능한 자율 주행 연습 환경을 만들고 새 기능의 유용성을 평가합니다.

### Communication과 UI

gateway/dashboard, 실제 ROS relay, 무선 통신, proxy와 서비스를 맡습니다. mock 시험과 새 환경에서의 웹 빌드는 독립적으로 시작할 수 있습니다. 전체 명령·상태 전달 경로는 다른 분야와 합쳐 확인해야 합니다. 운용자가 로버를 안정적으로 제어하고 상태를 파악할 수 있게 만드는 역할입니다.

### Manipulator·CAN·제어

ros2_control, 구동·조향, MoveIt Servo와 CAN 인터페이스를 맡습니다. mock과 lifecycle(상태 전환) 시험은 일찍 시작할 수 있습니다. 실제 장치를 움직이는 시험은 HW 담당자·운용자와 준비합니다. 로버의 움직임과 모드 전환을 검증하는 역할입니다.

### Perception과 영상

카메라 SDK/wrapper, 모델 빌드 절차, 추론과 GStreamer를 맡습니다. Nano의 환경 구성이 끝나면 실제 장치에서 연동을 확인합니다. NX 하드웨어 인코딩과 여러 기능을 동시에 실행했을 때의 부하는 NX에서 따로 검증합니다. 센서·추론 환경을 재현하고 운용 영상을 안정적으로 제공하는 역할입니다.

### 시스템 검증과 릴리스

SW·HW 공동 시험표, 운용 절차, 배포·복구 파일 묶음을 준비합니다. 계획은 초기에 세우고, 장비를 공유하는 실제 시험과 재시험은 일정을 조율해 순서대로 진행합니다. 각 분야의 결과를 합쳐 URC 2027에 사용할 로버를 검증합니다.

통합 담당자 한 명이 공통 launch, 메시지, TF, URDF, 운용 모드·센서·서비스 구성, 플랫폼 버전을 조정합니다. 각 작업에는 담당자와 검토자가 필요합니다. 리뷰 시간과 HW 담당자·운용자의 시험 참여 시간도 함께 계획해야 합니다.

## 먼저 배정할 세 가지 작업 {#먼저-배정할-세-가지-작업}

1. **현재 환경과 필요한 기능 확인:** NX에서 쓰는 소프트웨어와 설정을 기록합니다. SW·HW 담당자와 운용자가 첫 릴리스에서 지원할 기능과 운용 구성을 합의합니다.
2. **Nano 준비:** 장비를 가져와 구성을 기록하고 접근 방법을 정합니다. 운용 로버와 연결을 격리하고, 시험용 주변장치와 설치·복구 절차를 준비합니다.
3. **빌드와 기본 동작 재현:** 기존 환경과 새 환경에서 클린 빌드를 시도하고, 실제 Jetson에서 기본 동작을 확인하는 smoke test 하나를 준비합니다. 다른 팀원이 절차를 따라 같은 결과를 얻는지도 확인합니다.

세 작업은 겹쳐 진행할 수 있습니다. 첫 결과를 보면 실제로 막히는 선행 조건과 분야별 작업량을 더 정확히 알 수 있습니다. 아직 병합되지 않은 배포 작업도 어떤 부분을 가져올지 정해야 합니다. 조사한 브랜치에 이미 포함되어 있다고 가정하면 안 됩니다.

## 작업 시간과 인력을 계획할 때 {#시간과-인력에-관해-확인할-정보}

작업을 맡을 사람에게 주당 가용 시간, 예상 작업량의 범위, 추정의 확실성, 선행 조건, 외부 대기 시간을 확인합니다. 직접 구현하는 시간과 리뷰·장비 예약·부품 수급·NX 시험 일정 때문에 기다리는 시간을 구분하세요. 첫 설치와 포팅을 해 본 뒤 추정을 갱신합니다.

팀이 정한 URC 2027 준비 완료 시점과 통합 시험 일정에서 역산해 계획합니다. 공동 시험, 원인 분석, 수정, 재시험, 문서화, 복구 연습 시간도 확보합니다. 이 문서만으로 대회 일정이나 납기, 담당자의 투입 시간이 확정되는 것은 아닙니다.

## Codex에 맡길 수 있는 일 {#codex에-맡길-수-있는-일}

의존성 조사, 설치 절차 작성, 공식 안내에 따른 API·설정 수정, 필요한 시험 작성, 빌드, 실패 분석, 작은 PR 준비를 맡길 수 있습니다. 기준 소스 버전, 작업 환경, 바꿀 인터페이스, 확인할 결과, 로그를 남길 위치를 지정하세요.

실제 장비 구성과 보정값 확인, 장치·운동 시험 감독, 허용할 임무 동작 결정, 시스템 결과 승인은 사람이 맡습니다. 빌드 성공만으로 조향 방향, 실제 장애물 대응, 전체 부하에서의 안정성을 확인할 수는 없습니다.

## 다른 개발자에게 인계할 때 {#업무-인계-형식}

작업 목적과 결과물, 선행 조건, 담당자·검토자, 소스·환경 버전, 실행 절차, 통과 기준과 시험 결과, 중단·복구 조건을 남기세요. 자리를 비우거나 작업을 멈출 때는 마지막 결과, 브랜치/SHA, 해결할 질문, 다음 작업을 적습니다.

최종 로버 시험까지 기다리지 말고, 작은 end-to-end 시나리오를 일찍 합쳐 분야 간 연결을 확인합니다. 작업 준비에는 [개발 시작하기]({{< ref "docs/global-update-project/ko/start.md" >}}), 인계 형태에는 [컨트롤러 포팅 예제]({{< ref "docs/global-update-project/ko/controller-example.md" >}})를 참고하세요.
