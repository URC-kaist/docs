# 개발 시작하기 {#어디서-시작하나요}

마이그레이션 작업을 맡았다면 이 순서로 준비하세요. [프로젝트 개요]({{< ref "docs/global-update-project/ko/_index.md" >}}) · [English]({{< ref "docs/global-update-project/en/start.md" >}})

## 작업할 코드와 장비 확인하기 {#알맞은-작업-공간과-환경을-선택합니다}

| 항목 | 확인할 내용 |
| --- | --- |
| Jazzy 소스 | 준비된 로컬 저장소는 `~/mr2-stack-jazzy`, 기본 브랜치는 `main`입니다. 작업 전에 현재 commit을 확인하세요. |
| 비교할 기존 소스 | 조사한 upstream `2026`의 기준은 `74422f36…`입니다. 실제 NX에서 사용하는 코드와 설정은 별도로 확인해야 합니다. |
| 개발자 PC | Humble과 Noble/Jazzy 환경을 분리합니다. 셸과 빌드 결과물도 각각 사용합니다. |
| 실제 Jetson 시험 | Nano를 가져와 OS·의존성을 설치하고, 장비 접근을 준비한 뒤 진행합니다. |
| NX 로버 | 현재 운용 환경을 유지합니다. 운용을 중단해야 하는 시험은 합의한 시간에 진행합니다. |
| 협업 | SW 팀장이 작업을 배정합니다. 공통 인터페이스는 통합 담당자가 검토하고, 실제 장치 시험에는 HW 담당자와 운용자가 참여합니다. |

저장소를 준비할 때는 기존 애플리케이션 코드와 마이그레이션 안내 문서를 넣었습니다. Jazzy 설치나 빌드까지 끝났다는 뜻은 아닙니다.

## 먼저 소스를 살펴보고 시험 하나 정하기 {#지금은-조사와-작업-준비부터-시작할-수-있습니다}

아래 명령은 `~/mr2-stack-jazzy`에 저장소를 받아 둔 PC에서 실행합니다. 다른 경로를 사용한다면 경로를 바꾸세요. 현재 브랜치, commit, 서브모듈 버전만 확인하며 의존성 설치나 장치 실행은 하지 않습니다.

```bash
git -C ~/mr2-stack-jazzy status --short --branch
git -C ~/mr2-stack-jazzy log -1 --oneline
git -C ~/mr2-stack-jazzy submodule status
```

관련 코드와 설정, 해당 패키지의 마이그레이션 안내를 읽으세요. 어떤 입력을 받아 어떤 출력을 내야 하는지 확인하고, 이를 점검할 대표 시험 하나를 제안합니다. 리더와 함께 [GU-00부터 GU-12까지의 작업 초안]({{< project-resource "projects/global-update-project/issues.ko.json" >}})에서 관련 작업을 정하세요.

실제 장치를 쓸 시간이 아직 없어도 소스 조사, 장비·설정 목록 작성, 시험 설계, 설치 절차 초안은 진행할 수 있습니다.

## 코드 수정이나 공유 장비 변경 전에 맞출 내용 {#구현이나-공유-장비-변경-전에-확인합니다}

- **작업 범위:** 만들 결과, 담당자와 검토자, 기준 commit, 필요한 운용 모드·센서·서비스 조합, 공통 인터페이스 변경 사항을 정합니다.
- **시험 환경:** 준비된 환경이 무엇인지, 공유 설정과 주변장치를 누가 관리하는지 확인합니다.
- **확인 방법:** 어떤 결과와 로그를 남길지, PC·Nano·NX 중 어디서 추가 시험이 필요한지 정합니다.

최종 통합 기준, 사용할 이미지, 릴리스에 포함할 기능, 향후 기준 저장소는 팀이 결정합니다. 아직 정해지지 않은 부분은 가정을 적고, 그 결정에 의존하는 작업만 보류하세요. 독립적으로 할 수 있는 조사는 계속 진행합니다.

## 리뷰할 수 있도록 결과 남기기 {#검토-가능한-결과를-돌려줍니다}

리뷰를 요청할 때는 다음 내용을 남기세요.

| 항목 | 남길 내용 |
| --- | --- |
| 변경 내용 | 브랜치와 SHA, 작은 diff 또는 변경 제안 |
| 실행 환경 | OS·의존성·설정 버전 |
| 재현 방법 | 실제로 실행한 명령, 기대한 결과와 관측한 결과 |
| 결과 파일 | 로그와 산출물 목록(manifest), 각 파일의 위치 |
| 남은 일 | 추가로 필요한 장비 시험과 다음 작업 |

실행하지 않은 절차는 제안이라고 표시하세요. 실패했더라도 다른 사람이 같은 조건에서 재현할 수 있으면 유용한 결과입니다.

소프트웨어 시험을 통과하면 해당 결과를 기록합니다. NX나 실제 장치에서 확인해야 할 항목은 별도 작업으로 연결해 남깁니다. API를 옮기는 작업에 planner 튜닝이나 프로토콜 재설계까지 섞지 말고, 그런 동작 변경은 작업 범위에 포함되는지 먼저 정하세요.

## 누구와 협의하나요? {#누구와-협의할지-구분합니다}

Codex에는 범위가 명확한 소스 조사, 수정, 빌드, 시험, 결과 정리를 맡길 수 있습니다. 사람과 협의할 대상은 다음과 같습니다.

| 상황 | 협의할 담당자 |
| --- | --- |
| 여러 분야가 공유하는 인터페이스 변경 | 통합 담당자 |
| 공유 Nano의 OS·설정 변경 | 장비 담당자 |
| 장치나 로버를 실제로 움직이는 시험 | HW 담당자와 운용자 |
| NX의 운용 환경 전환 | 팀이 지정한 릴리스 승인 담당자 |

[컨트롤러 포팅 예제]({{< ref "docs/global-update-project/ko/controller-example.md" >}})에서 코드 조사부터 결과 인계까지의 형태를 볼 수 있습니다. 아직 실행하지 않은 작업을 설명하는 예제입니다.
